# @tokovo/dsl

The TypeScript authoring API for Tokovo episodes.

## Responsibilities

- episode builders
- device and OS setup
- plugin-owned app snapshot and initial-view authoring
- app-track, cinematic-program, audio, overlay, and device-track entrypoints
- compiler-plugin wiring from authored episodes

Use `@tokovo/dsl` for deterministic scene timing and sequencing.

## Role In The Stack

`@tokovo/dsl` is the primary authoring surface before compilation. It should stay expressive and
deterministic without turning into a CMS abstraction layer.

## Core Model

Tokovo v1 does not use beat-based authoring. The authoring model is:

- `device()` for device and OS state
- `snapshot()` for plugin-owned pre-seeded app data
- `view()` for explicit frame-0 app routing
- named built-in app methods for app mutations after frame 0
- `track()` as the low-level extension point for external app plugins
- `cinematics()` for immutable StageProgram and CameraPlan data
- `audio()`, `overlay()`, `os()`, and `deviceTrack()` for supporting direction
- `input()` for explicit field-scoped text sessions
- `notificationTrack()` for notification delivery and interaction

## Bootstrap Rules

- `device()` is only for device/OS state
- `snapshot()` is only for plugin-owned previous app data
- `view()` is only for explicit frame-0 app routing

The DSL should not synthesize conversations, feeds, or threads through device state.

Checked-in episodes use the product-level builder from
`@tokovo/episodes/code-first-episode`. Its named app methods own FPS and declaration-order
plumbing so episode authors never instantiate app track builders directly.

The product-level layer also owns narrative composition: actors with per-app identities,
scene-local timing, consistent conversation/social verbs, and typed story handles. Story APIs
lower into event IR, while `cinematics()` stays an independently signed projection program; neither
introduces a second runtime or nondeterministic scheduling model.
